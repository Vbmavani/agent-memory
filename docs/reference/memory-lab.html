How AI agents remember

A guide to the kinds of memory an agent can have, the decisions every memory system makes, and labs you can run yourself, first by changing Claude Code and then by building your own harness.

The core idea An LLM is stateless. Between API calls it remembers nothing. Everything an agent "remembers" is either in its weights from training, or put back into its context window by the harness on every call. Agent memory is the harness deciding what to store, where, and which pieces to load back at the right moment. That is why changing the harness is the way to learn it.
Part 2

Types of memory

Most people use the taxonomy from the CoALA paper (Sumers et al., 2023), which borrows from human cognitive science.

TypeHuman analogyIn an agentExample
ParametricInstinct, general knowledgeKnowledge baked into the weightsKnowing what Python is
WorkingWhat you're holding in mind nowThe current context window: system prompt, messages, tool resultsThe file it just read
Short-termThe last few minutesThis session's message history, maybe trimmed or summarized"As I said earlier…"
Episodic"I remember that time when…"Records of past events and sessions, with time and outcome"Last Tuesday's deploy failed because of X"
SemanticFacts you knowLasting facts about the user, project or world"User prefers TypeScript"
ProceduralKnowing how to ride a bikeHow to do things: instructions, skills, learned workflows, codeCLAUDE.md rules, Skills, a saved-script library

Other terms you'll see

Scratchpad / notesThe agent writes notes to a file while it works, like NOTES.md or a todo list.
Entity memoryFacts grouped by entity: a person, repo or customer.
Graph memoryFacts as subject → relation → object, often with time attached (Zep/Graphiti).
Retrieval (RAG)A large external store searched by embeddings or keywords.
Shared memoryOne store that several agents read and write.
Cache memoryKV cache and prompt caching. About speed and cost, not meaning, but it shapes memory design (Lab 10).
Part 3

The five operations every memory system does

Whatever framework you use, it is making these choices. Learning memory mostly means learning these trade-offs.

  1. Write: what to store, and when

    • Hot path: the agent saves during the conversation through a "remember" tool.
    • Background: a separate process reads transcripts later and extracts memories.
    • Store everything and you get noise. Store too little and you get amnesia.

  2. Read: what to load, and when

    • Always loaded: CLAUDE.md, or a user profile in the system prompt.
    • Retrieved on demand: search by relevance, recency or importance.
    • Agent-pulled: the agent calls search_memory when it decides it needs to.
    • Generative Agents (Park et al., 2023) scores each memory as recency + importance + relevance.

  3. Update and consolidate

    • Merge duplicates, fix contradictions ("moved from Mumbai to Pune"), and turn many episodes into one fact. This is called reflection.

  4. Forget

    • Decay over time, TTLs, deleting wrong memories, and privacy deletion.

  5. Compress

    • Summarize or prune what's in the context window so a long task fits: compaction, context editing, sliding windows.
Part 4 · Track A

Change Claude Code's memory

No code needed. Claude Code is a real production harness, and its memory is mostly plain files you can edit.

LAB 01Procedural memory through CLAUDE.mdAlways-loaded instructions and their precedence▶

Files Claude Code loads at startup:

  • ~/.claude/CLAUDE.md: global, for all projects
  • ./CLAUDE.md: project level, committed to git
  • ./CLAUDE.local.md: personal, not committed, where supported
  • CLAUDE.md files in subfolders, loaded when Claude works there
  • @path/to/file.md imports another file into CLAUDE.md

Exercise: in a test project, add a rule like "Always write commit messages as type(scope): msg". Start a new session, ask for a commit message, and check the rule was followed. Then put a global rule and a project rule in conflict and see which wins.

You learnAlways-loaded memory, precedence, and that every line costs tokens on every turn.

LAB 02Semantic memory through auto-memoryAn index file plus one file per fact▶

Claude Code keeps a per-project memory folder at ~/.claude/projects/<project>/memory/: one .md file per fact with frontmatter (name, description, type: user / feedback / project / reference), plus a MEMORY.md index loaded into every session.

Exercise: say "remember that I prefer pnpm over npm". Open the folder and read what it wrote. Edit it by hand. Delete it and check the memory is gone. Then plant a wrong memory and watch how it affects later sessions.

You learnThe index-plus-details pattern, memory types, and how stale or wrong memories cause harm.

LAB 03Short-term memory: compact, clear, resumeWhat survives a summary▶
  • /compact summarizes the conversation. Add focus, like /compact keep the API design decisions.
  • /clear wipes working memory.
  • claude --continue and claude --resume reload past sessions, a form of episodic memory.

Exercise: have a long session, compact it, then ask about a detail from early on. What survived? Compare with /clear.

You learnSummaries lose information, and what they keep is a design choice.

LAB 04Change the harness with hooksThe main way to modify Claude Code without forking it▶

Hooks are scripts the harness runs at lifecycle events, configured in settings.json.

  • SessionStart → print recent git log plus notes/today.md. The output becomes context. You built retrieval at session start.
  • PreCompact → save the transcript to episodes/<date>.md before it's summarized. You built episodic memory that survives compaction.
  • Stop / SessionEnd → run claude -p "Extract durable facts from this transcript" and append to a facts file. You built background extraction.
  • UserPromptSubmit → grep your notes for words in the prompt and inject matches. You built per-turn RAG.

TipAsk Claude to use the update-config skill to wire these into settings.json.

LAB 05Procedural memory through Skills and subagentsProgressive disclosure and memory isolation▶
  • Skills are folders with a SKILL.md. Only the description loads up front; the full body loads when relevant. Lots of procedural memory, small context cost.
  • Subagents have their own context windows. What does a subagent know about the parent's conversation?

Exercise: turn a workflow you repeat into a skill, then compare token use with putting the same text in CLAUDE.md.

Part 4 · Track B

Build your own harness (Python)

Install with pip install anthropic. Use claude-opus-5-5, or claude-haiku-5-5 for cheap experiments.

LAB 06Bare loop, no memorySee statelessness for yourself▶

Write a 20-line chat loop that sends only the latest user message. Watch it forget your name. Then append every message to a messages list and watch it remember. This is all that short-term memory is.

LAB 07Manage short-term memory by handSliding window vs. summary buffer▶

Write three versions and compare them on a 50-turn conversation:

  • Sliding window: keep only the last N messages.
  • Summary buffer: when history passes X tokens, summarize the older turns and replace them.
  • Summary plus recent: a running summary followed by the last N turns verbatim.

Measure cost with client.messages.count_tokens and check recall with questions about early turns.

LAB 08Long-term memory as a toolAgent-controlled save and search▶

Give the model your own tools, save_memory(text, type) and search_memory(query), backed by a JSON file or SQLite. Run the tool loop.

  • When does the model choose to save? Change the system prompt and watch it change.
  • Search v1: keyword matching. v2: embeddings (e.g. sentence-transformers locally). v3: Generative Agents scoring, α·recency + β·importance + γ·similarity.
LAB 09Anthropic's built-in memory toolClaude manages a /memories folder; you supply the storage▶ 
import anthropic
from anthropic.lib.tools import BetaAbstractMemoryTool

class FileMemory(BetaAbstractMemoryTool):
    # Map each command to a real folder on disk (e.g. ./memories)
    def view(self, command): ...
    def create(self, command): ...
    def str_replace(self, command): ...
    def insert(self, command): ...
    def delete(self, command): ...
    def rename(self, command): ...

client = anthropic.Anthropic()
runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=16000,
    tools=[FileMemory()],
    messages=[{"role": "user", "content": "Remember I'm learning agent memory, and I prefer Python."}],
)
for message in runner:
    print(message)

Exercise: start a brand-new conversation and ask "what do you know about me?". Open the folder to see how Claude organized its own memory.

Safety: check paths so the model can't write outside the memory folder.

LAB 10Context editing, compaction and cachingManaging working memory on long runs▶

Context editing removes old tool results so long agent runs stay small:

client.beta.messages.create(
    model="claude-opus-5-5", max_tokens=4096,
    betas=["context-management-2025-06-27"],
    context_management={"edits": [{"type": "clear_tool_uses_20250919"}]},
    tools=[...], messages=[...],
)
  • Server-side compaction (beta compact-2026-01-12) summarizes near a token threshold. Append the full response.content back into messages, not just the text, or the compaction state is lost.
  • Prompt caching: put stable memory (profile, rules) first and volatile memory (retrieved snippets, timestamps) last. Check usage.cache_read_input_tokens.

Exercise: run one 100-tool-call task four ways: no management, context editing, compaction, and compaction plus the memory tool. Compare tokens and success rate.

LAB 11Reflection and consolidationA "sleep" step between sessions▶

After each session, a second model call reads the episode log and:

  • pulls out new semantic facts,
  • merges or overwrites contradicting facts,
  • writes lessons learned, like Reflexion's self-critique, as procedural memory.

Plant contradictions on purpose (change your stated city) and test whether the newest fact wins.

LAB 12Evaluate your memoryThe step most people skip▶

Write 20 to 30 test cases: "In session 1 the user says X. In session 3, ask Y. The answer should use X." Score:

  • Recall: does it remember what it should?
  • Precision: does it bring up irrelevant old facts?
  • Staleness: does it use outdated facts?
  • Token cost per answer.

Public benchmarks to look at: LongMemEval, LoCoMo, MemoryAgentBench.

Part 5

Reading list, in order

  1. Generative Agents (Park et al., 2023) memory stream, retrieval scoring, reflection
  2. MemGPT (Packer et al., 2023) virtual context management
  3. Reflexion (Shinn et al., 2023) learning from verbal self-feedback
  4. Voyager (Wang et al., 2023) a skill library as procedural memory
  5. CoALA (Sumers et al., 2023) the unifying taxonomy
  6. Anthropic engineering posts on context engineering and building effective agents, plus the docs for the memory tool, context editing and compaction
  7. A recent survey search "memory mechanisms LLM agents survey"
