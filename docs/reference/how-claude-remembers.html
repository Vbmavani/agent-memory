How Claude remembers

An AI agent forgets everything when a conversation ends. Anthropic's post explains how Claude keeps useful knowledge from one session to the next, and why the trick that works best is a lot like sleep.

The problemEach new session starts blank. Claude has to decide what to write down for later, without knowing what later will need.
Part oneDuring work, Claude writes short memory notes. Newer models are much better at choosing what's worth saving.
Part twoBetween sessions, Claude re-reads old transcripts and cleans up its memory. Anthropic calls this dreaming. It fixes wrong notes, builds wikis, and decides what to load up front.

Source: “The components of agent memory” by Lance Martin, Anthropic Engineering

What problem is this solving?

Think of hiring a very capable assistant who has total amnesia every morning. They're smart, but each day they re-learn your preferences, repeat yesterday's mistakes, and rediscover the same shortcuts. That's an AI agent without memory.

The fix sounds easy: let the agent keep a notebook. The hard part is what goes in it. Write too little and the useful lessons are lost. Write everything and the notebook turns into a junk drawer that costs more to search than it saves. And a note that was wrong, or went out of date, can mislead every future session that trusts it.

The post opens with Kierkegaard's line that life is understood backward but lived forward. Memory has the same bind: you choose what to save before you know what will matter.

In this post, agent memory means knowledge Claude picks up from experience (talking with people, doing tasks) and saves as text it can read in a later session. Three things that sound similar are left out:

TrainingWhat's baked into the model's weights. Fixed after training.
In-conversation learningWhat Claude picks up within one chat. Gone when it ends.
CompactionSummarizing older turns so a long task fits. Same session, not memory across sessions.

The big idea

Borrowed from how people sleep

Your brain records experiences quickly during the day, but only some of them become lasting knowledge. A lot of that sorting happens offline, during sleep or quiet rest, when the brain replays recent events and files the important ones into long-term memory. Experiences tagged as important get replayed more.

The idea builds on "sleep-time compute," proposed by Letta and UC Berkeley: use the idle time between conversations to reorganize what the model already has.

The components

Memory is a stack of four layers

The "components" in the title are these layers. Lower layers hold more and are slower to use. Higher layers are smaller and closer to hand. The top one is loaded into every session automatically.

Part one · while working

Memory notes: deciding what to write down

Writing a note is a bet that it will matter again. Recording a fact you've already checked is a bet that a future session will want to use it without checking again. The post's main finding here: newer Claude models make much better bets.

Test 1: a database quiz with memory

On a benchmark called CL-Bench, Claude answers questions by querying a database. After each answer it's told the right solution and can save notes. Every question starts a fresh session, and the only thing that carries over is the folder of notes. The ideal habit is a loop: get it wrong, guess why, test the guess, and save a proven rule.

What changed between models was the quality of their notes, not just the score:

Sonnet 4.6Scattered files full of untested guesses. Often didn't even read its own notes.
Opus 4.7Merged notes into one reference doc and marked which facts were checked.
Sonnet 5Marked answers as confirmed once graded, and wrote corrections after mistakes.
Opus 5First to close the loop: each note had a rule, how it was proven, and warnings about traps.
5.5 modelsAlso closed the loop. Started higher without memory and ended about level with Opus 5.

Test 2: playing Pokémon Red

Each model got a folder to keep notes while playing. Compared after about 10,000 game steps:

A separate file for every battle, item and character. The game changes constantly, so the notes went stale. At one point it spent 17 steps creating and deleting files without playing at all.

Skipped anything visible on screen anyway (money, map position). Saved only what it had to work out: plans, strategies, tested rules, plus a one-page dashboard of its current goal.

A nice example of a learned rule: after seven failed attempts to catch a Magikarp, Claude wrote "if three or more Poké Balls fail in a row, change the timing by waiting a little." The very next catch worked.

Practical tip from the post

Tell Claude what memory is for, not how to use it. For strong models, just saying "a memory folder exists" was enough. Adding strict rules like "only record failures" actually made Opus 5 worse (its gain dropped by 0.23).

Older models are the exception. Telling Sonnet 4.6 to read its notes first and to test its theories nearly doubled its score, from 0.33 to 0.64.

Part two · between sessions

Dreaming: tidying memory after the fact

Notes written mid-task are a guess about what will matter, made with only that session in view. Dreaming is a separate pass that runs later, re-reads the full transcripts, and improves the memory with hindsight. The post describes five jobs it does.

1

Correct wrong notes

Fixed note → reached the next city at action 1,935 · Unfixed → never got there

In Pokémon, Claude wrongly noted which side of Mt. Moon a landmark was on, declared the area "DONE," and kept falling off a one-way ledge back to the start. It looped three times, then walked all the way back to the previous town.

Dreaming checked the note against the transcript, caught the error, and rewrote it. With the corrected note, Claude went straight through.

2

Build a wiki out of raw material

Wiki alone: 13% → 48% of answers · Wiki + search: 61% vs 53% search only

Anthropic pointed dreaming at about 350,000 files (around 420 million tokens) from Stainless, a company it acquired. Over 128 sessions, Claude agents explored files and wrote linked wiki pages, like a new employee slowly becoming a veteran. The wiki grew from 103 pages to 222, with links going from 766 to 12,893. Using wiki plus search also saved about 20,000 tokens per question.

On legal merger questions that needed facts from several documents, the wiki scored 87% against 73% for search alone. It didn't help when the answer sat in one document anyway. And on a tiny 10-document set, the wiki came out 1.77× larger than the originals, which defeats the point of a summary.

3

Promote the most important notes to the top

Rule: keep the always-loaded layer small

The top layer is loaded into every session, so Claude doesn't need to go looking. But it costs space every time, a wrong note there spreads everywhere, and long instruction files get followed less reliably. So much of dreaming's work is moving detail down and leaving a short index on top. Claude Code, for example, only loads the first 200 lines (or 25 KB) of its MEMORY.md file.

4

Focus memory on a goal

Contract facts kept: 41 of 57 (72%) → 57 of 57 (100%)

With generic instructions, several agents edited one shared table of contract terms at once and overwrote each other's work. Claude then reviewed its own failures and rewrote the instructions: one page per contract, one writer per page, terms quoted word for word. Every graded fact survived.

5

Fill gaps a single session can't see

Links: 225 → 278 · Pages: 38 → 41

Because dreaming looks across many sessions, it can spot shared patterns and loose ends. A second pass found nine links pointing to a missing page, redirected them to the page that already covered it, and added three pages nobody had written.

Still unsolved

Open questions

When should memory be written?Writing during the task captures the moment while it's fresh, but distracts from the task. Dreaming later keeps the task clean, but the lessons aren't ready right away.
How do you keep memory current?Notes go stale as the world changes. Re-checking everything is expensive, so one idea is to re-check only what's likely to change, or what gets used most.
What's the foundation?The full transcripts plus search are the base. Wikis on top help, but they need upkeep so errors don't pile up.

The post's conclusion: no model can truly know what future sessions will need. Better judgment helps in the moment, and dreaming lets Claude look back and fix what it got wrong.

If you build with agents

What to take away

  1. Give the agent a place to keep notes, and tell it what the notes are for. With current models, skip the detailed rules.
  2. Keep the full transcripts. They're the record you check every note against.
  3. Keep the always-loaded memory short: an index that points to details elsewhere.
  4. Run a periodic clean-up pass that fixes stale notes and links things together. Aim it at a specific goal.
  5. Build a wiki only when answers span many documents. For small or simple sources, search is enough.

Anthropic links two starter guides from the post: a dreaming cookbook and a knowledge-wiki quickstart (under managed-agents/knowledge-wiki).

Words used above

Quick glossary

Session
One conversation or task run. Memory is what survives from one session to the next.
Transcript
The complete log of what happened in a session.
Salience
How important something seems at the time. Deciding salience is deciding what to write down.
Context
Everything the model can see right now. Space is limited, so what's loaded matters.
Token
A chunk of text, roughly ¾ of a word. A measure of size and cost.
Benchmark
A standard test used to compare models. CL-Bench tests learning over many tasks.
